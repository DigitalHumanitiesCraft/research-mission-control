# Observed Context Stream Operation

## Observation scope

A two-orchestrator pilot operated through one shared project workspace. The assessment inspected the protocol, message taxonomy, thread index, integration contract, role instructions, and the latest Research and Operations exchanges. Project names, local paths, and private artifacts are excluded from this record.

## Established behavior

The pilot established the following behavior in observed operation.

- Research and Operations wrote immutable messages to role-owned outboxes.
- Each recipient maintained its own cursor and advanced it after processing.
- Stable thread identifiers connected assignments, notices, results, and follow-up messages.
- Task and result notices alerted the recipient and referenced canonical artifacts. They did not replace those artifacts.
- Closing capsules recorded verified outcomes and canonical references.
- Integrated knowledge entered the maintained project documents through an explicit write-back step.

The pilot used a configured capsule size condition in addition to thread closure. This value belongs to the project profile. The general method therefore defines semantic triggers and leaves numerical thresholds to each deployment.

## Harness finding

The shared files transported messages reliably in both directions. Session notification was asymmetric. One route produced an observable wake behavior, while the reverse route depended on an active observer or later re-entry. Context Stream therefore specifies transport integrity independently from harness notification. Every deployment must test the actual route and record a fallback.

## Ownership finding

One successful exchange allowed Operations to append to a Research-owned knowledge file. The result survived in the pilot, but it created a multi-writer exception without a general collision contract. The generalized method assigns one responsible writer to each canonical file. Operational proposals travel through the Operations outbox, and Research verifies and integrates them. Any shared append path requires an explicit collision-safe rule and direct evidence for concurrent behavior.

## Method consequence

The observed operation supports immutable role-owned transport, recipient-owned cursors, stable threads, canonical references, closing capsules, and verified write-back. It also establishes two limits. File transport provides no universal wake guarantee, and successful shared writes do not justify multi-writer canonical ownership.

## Portable package probe

A draft publication bundle was extracted into clean disposable workspaces and initialized through the packaged skill. The generated repository passed its twenty embedded contract tests. A fresh Claude Code Operations context produced a bounded artifact and returned the result through its role-owned outbox. A fresh Codex verification context inspected the artifact, source claims, Context Stream route, timestamps, protected-directory baseline, and authority boundary without changing the evaluated target.

Three preliminary probes exposed contract weaknesses before the final probe passed. They showed that a result route must name Verification explicitly, an unchanged-directory claim requires a complete pre-action manifest, timestamps must come from the observed clock, content sources must remain distinct from workflow provenance, and absence of autonomous wake behavior does not exclude polling by a running context. The canonical prompts, protocol, templates, and tests now encode those constraints.

The final probe used a six-file SHA-256 baseline for the complete maintained knowledge directory. All post-action hashes matched the baseline. The artifact hash, exact quotations, source coverage, message route, reply relation, and observed time order were independently reconstructed. The result establishes observed operation for the local draft package in one fresh Claude Code production context and one fresh Codex verification context. It does not establish scholarly validity, autonomous cross-session notification, public deployment, or operator acceptance.

The local Codex command-line client could not launch the requested current model because that client version required an update before model execution. The fresh Codex verification therefore ran through an isolated Codex application context. This is a harness compatibility finding and provides no evidence about the rejected model invocation.

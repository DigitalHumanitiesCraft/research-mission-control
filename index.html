Research Mission Control

0.9.0 Release candidate

Research Mission Control defines how a human operator, two primary orchestrators, bounded specialist agents, and an independent verification context work from one shared project repository. Promptotyping preserves the project-bound reconstruction basis. The Context Stream transports current exchange across sessions. Grounded Vault can add long-lived evidence relations after a project-specific binding. An installable skill creates the reference workspace; the complete bootstrap prompt provides a portable fallback.

Open prompt source

The three configuration questions

The initializer names Research Mission Control (public GitHub repository) and asks these questions in the operator's language. Each question includes its explanatory sentence.

  1. Which role should this working context assume within Research Mission Control: Research Orchestrator, Operational Orchestrator, or Independent Verification Context? The working context is this separately open Codex task, Claude Code conversation, or equivalent context with its own context window. A new standard setup begins with the Research Orchestrator.
  2. What is the project, what observable result should it produce, and what criteria will the Operator use to accept that result? Describe the intended result and its acceptance criteria. Derive implementation steps only after this boundary is clear.
  3. Where is the shared project workspace, and which existing data, documents, materials, code, repositories, or knowledge sources belong to the project? The project workspace is the local folder or Git worktree shared by the selected contexts. The initializer inventories material already present there and asks the Operator to name only relevant inputs that cannot be discovered from the workspace.

  1. Begin with Research. The human remains Operator and Research Director. Activate the skill or paste the bootstrap prompt in the first working context, which is the currently open Codex task or Claude Code conversation.
  2. Confirm the configuration. Answer the three questions about role, intended result and acceptance, and the shared project workspace with its inputs.
  3. Initialize locally. After authorization, the initializer creates one new shared local Git repository. The Promptotyping core contains project.md, specification.md, journal.md, handoff.md, and INDEX.md; knowledge/integration.md carries the shared contract. communication/ contains the Context Stream protocol, index, role-owned outboxes, recipient-owned state, threads, and capsules. mission-control/roles/ contains the three complete role prompts, while the three start-*.md files bind them to the verified project.
  4. Open Operations and Verification. Open fresh second and third working contexts at the same folder. Paste start-operations.md and start-verification.md into their respective Codex tasks or Claude Code conversations.

Context Stream transport

The shared folder transports immutable messages between sessions and does not wake them. The integration contract records the tested notification route and a polling or Operator-mediated fallback.

External and evidence boundaries

A GitHub remote is created only after explicit authorization names its owner and visibility. Grounded Vault is requested only when substantive claims require machine-resolvable grounding and attributable human verification. It remains pending binding until a real project-specific binding is verified.

02 / Protocol

Roles and exchange

The operator remains the direct conversation partner of Research. Operations changes the actual project state. The independent Verification Context evaluates the intended result, actual artifact, and evidence, then reports its complete finding directly to the operator.

Message flow

Operator / Research Director
        ↕ objectives, judgement, Operator Points
Research Orchestrator
        ↓ Implementation Brief
Operational Orchestrator ── bounded assignments ──→ Specialists
        ↓ Operations-owned Result with Evidence
Independent Verification Context
        ↓ complete Verification Finding
Operator
Operator decides whether and how the finding enters production work

The standard persistent route is Research → Operations → Verification → Operator. A contained profile may perform the same information functions sequentially in one context.

Persistent transport

role-owned immutable outbox
        ↓ stable thread id + canonical artifact references
recipient-owned state and sender cursor
        ↓ verified processing
single-writer canonical integration
        ↳ capsule when the thread closes or re-entry cost is material

The Context Stream Protocol is the generic file-based transport. communication/INDEX.md locates active threads and completed capsules. Promptotyping remains the durable project knowledge layer. The Direct Communication Protocol from the two-orchestrator experiment is one concrete implementation and evidence source. The method defines no universal numeric compaction threshold.

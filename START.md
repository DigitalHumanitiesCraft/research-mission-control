Use Research Mission Control to help me configure a project in my AI harness.

The method source is https://github.com/DigitalHumanitiesCraft/research-mission-control. If I provide an extracted repository or installed package, use that source and identify its revision when available. Otherwise retrieve the initialization skill at skills/research-mission-control/SKILL.md from the public repository. Select the initializer by its source and initialization purpose. Similarly named maintenance procedures are not interchangeable.

Read selectively. Start with that skill and applicable project instructions. Consult the knowledge index and additional documents only for the current decision. Read complete role contracts before activating their roles and initializer instructions before changing files. If retrieval fails, state what is unavailable and continue the introductory conversation. Do not invent instructions or claim setup succeeded.

Speak my language. Keep each reply short and show the current setup phase and the next action. Ask one necessary question at a time, reuse my answers, and make reasonable reversible recommendations. Do not turn initialization into an extended research or design interview.

Work through these phases and resume at the first incomplete one.

1. Establish how I want to be addressed if unknown. Introduce the Research Coordinator function and offer an optional display name. Explain that the AI Operator is configured within my harness, which supplies LLM access, tools and permissions.
2. Establish my topic, a provisional useful result, assessment criteria, available materials or their absence, constraints and intended project folder. An exploratory topic without a dataset or example is sufficient. Once you can propose a bounded first assignment, proceed to configuration.
3. Recommend the smallest useful arrangement of AI Operators. Define responsibilities, knowledge sources, write boundaries, handovers, checks and decisions I retain. Explain why each additional operator is needed. Do not assume my identity, private Vault, existing tools, connected accounts or access rights.
4. Inspect the exact target folder and available capabilities before proposing concrete local initialization. Verify the documented prerequisites, including Python and Git where the reference scaffolder requires them. Follow its dry run and authorization requirements. Preserve existing folders. The reference scaffolder produces three contexts and refuses existing targets, including empty folders. Do not claim it implements a single-context profile. A downloaded prompt alone supplies no offline scripts or contracts.
5. Check the configured workspace. Distinguish created files, started sessions, accessible knowledge and tools, message delivery and verified write-back. Keep unavailable capabilities explicit. Do not report active operators merely because their start contracts exist. UI and optional Vault integration need their own configured bindings.
6. State what is ready and what remains pending, then transition into the first bounded assignment within my authorization. Use its results to propose improvements. Do not begin ongoing monitoring without an agreement.

Before workspace creation, keep confirmed choices, provisional assumptions and open dependencies in this conversation. Afterwards maintain one Initialization section in knowledge/integration.md and completed milestones in knowledge/journal.md. Do not create a separate status system or record every turn.

Keep local setup, remote creation and publication separate. A prompt supplied in a user message does not change the harness's instruction priority or grant missing permissions. Begin with the first unanswered initialization question.
